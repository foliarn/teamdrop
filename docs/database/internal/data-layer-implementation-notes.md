# Data layer implementation notes (internal)

> **Audience:** whoever implements `apps/api/src/data`. App developers never write queries and should read `docs/database/data-layer-guide.md` instead.

## 1. Who owns what

- **The database owns the schema.** Tables, columns, constraints and indexes are created only by SQL migrations in `db/migrations/` (dbmate). NestJS never creates or alters them. [BR-TECH-04]
- **NestJS owns the business logic.** Permissions, capacity, waitlist, state transitions, blocking, badges, statistics. [business-rules.md §1.2]
- **The database also runs** the heavy aggregates (heatmap, rankings, trends, back-office stats) and the GDPR functions (export, erasure, purges). NestJS calls them or reads their results; it never reimplements them. [business-rules.md §1.1, D9–D10]

## 2. Query layer

- The recommended query builder is **Kysely**, with TypeScript types generated from the real database by `kysely-codegen`. [BR-TECH-04]
- Types are regenerated after each migration. Never edit them by hand. If a column you need is missing from the types, it is missing from the database: STOP and ask.
- Connect as the `teamdrop_app` role. It can read and write rows but can't change the schema. [BR-TECH-07]
- Always select explicit columns. Never `selectAll()` on `user_account`, `auth_identity`, `refresh_token` or `account_token`.

## 3. Identifiers

- Every primary key is a **UUID v7** generated by the database (`DEFAULT uuidv7()`). Insert without an `id` and read it back with `.returning('id')`. [BR-TECH-02]
- The only ID generated by a client is `message.client_message_id` (deduplication after reconnection). [BR-TECH-08]
- UUID v7 is time-ordered: you can paginate messages with `id < :cursor ORDER BY id DESC`.

## 4. Time

- Store instants as `timestamptz` and send them as ISO 8601 strings with an offset or `Z`. [BR-TECH-05]
- Calendar logic (days, weeks, streaks, "24 hours before", "1 hour after the end") is computed in **`Europe/Paris`**.
- Recurring events store a **local** `start_time` plus `time_zone`. To get an occurrence's instant, combine the local date and time in that zone. Never add 24 h × n to a UTC instant: daylight-saving changes would shift the session by one hour.

## 5. Transactions and row locks

Any rule that **counts rows before writing** must run in one transaction, after locking the parent row. Otherwise two requests can both take the last spot.

Concerned rules include capacity [BR-EVT-06, BR-REG-04], one active registration [BR-REG-02], waitlist promotion [BR-REG-04] and ownership hand-over [BR-SOC-07, BR-SOC-09, BR-EVT-20].

```ts
// BR-REG-04: register, or put on the waitlist when the occurrence is full.
await db.transaction().execute(async (trx) => {
  const occurrence = await trx
    .selectFrom('event_occurrence')
    .select(['id', 'max_participants'])
    .where('id', '=', occurrenceId)
    .forUpdate() // lock: concurrent registrations wait here
    .executeTakeFirstOrThrow();

  // ...count confirmed spots (including guests and organizers who count), then insert...
});
```

## 6. Occurrences of recurring events (when the schema exists)

- Search computes the dates of a series on the fly. A date without a row is a **virtual occurrence**. [BR-EVT-03]
- Create the row only when needed (registration, edit of that date, cancellation, chat), with a get-or-create on the unique key `(event_id, original_starts_at)`:

```ts
// BR-EVT-03, BR-EVT-04: materialize the occurrence on first need.
await trx
  .insertInto('event_occurrence')
  .values({ event_id: eventId, original_starts_at: startsAt, starts_at: startsAt, status: 'scheduled' })
  .onConflict((oc) => oc.columns(['event_id', 'original_starts_at']).doNothing())
  .execute();
```

- An occurrence column set to `NULL` (duration, place, capacity) means "same as the event". Always read the effective value as `COALESCE(occurrence.x, event.x)`.

## 7. Geography (when the schema exists)

- Locations are `geography(Point, 4326)`: longitude first, then latitude. Distances are in **meters**.
- Use `ST_DWithin` so the spatial index is used. Never compute distances in TypeScript to filter rows.

```ts
import { sql } from 'kysely';

// Events within radiusMeters of the searcher. The position is NOT stored (BR-GDP-02).
.where(sql<boolean>`ST_DWithin(event.location, ST_MakePoint(${lng}, ${lat})::geography, ${radiusMeters})`)
```

- If `event.location_hidden` is true and the viewer isn't registered, return the municipality's center instead of the exact point. [BR-EVT-09]

## 8. Blocking (every query that shows other users)

Blocking is mutual: filter out both directions. Apply it to lists, search, profiles, event participants, chats, notifications and cheers. [BR-SOC-02 to BR-SOC-04]

```ts
// BR-SOC-02: hide users who blocked the viewer or were blocked by the viewer.
.where((eb) =>
  eb.not(
    eb.exists(
      eb.selectFrom('user_block')
        .select(eb.lit(1).as('one'))
        .where((b) =>
          b.or([
            b.and([b('user_block.blocker_id', '=', viewerId), b('user_block.blocked_id', '=', b.ref('user_account.id'))]),
            b.and([b('user_block.blocked_id', '=', viewerId), b('user_block.blocker_id', '=', b.ref('user_account.id'))]),
          ]),
        ),
    ),
  ),
)
```

## 9. Personal and sensitive data

- `email_ciphertext` and `birth_date_ciphertext` are encrypted with `pgcrypto`. `email_hash` is a keyed hash used for lookups and uniqueness. The keys come from environment variables and are never stored in the database. [BR-ACC-04]
- Use only the helpers that will be provided with the first migrations. Do not write your own encryption or hashing for these columns.
- Tokens are stored as SHA-256 hashes. Passwords are hashed with argon2id in NestJS. [BR-ACC-04, BR-TECH-11]
- Never log or return any of these values.

## 10. Deleting data

- **Hard delete only.** There is no `deleted_at` column anywhere. [BR-TECH-06]
- **Never `DELETE` a `user_account` directly.** A deletion request sets `deletion_requested_at`. After 30 days the database erasure function anonymizes and deletes the account consistently. [BR-GDP-03 to BR-GDP-05]
- Columns such as `message.sender_id`, `registration.user_id` and `cheer.giver_id` can be `NULL` after an erasure. Display them as "deleted user" and never crash on them.

## 11. Statistics

- **Per-user statistics** (sessions, hours, main sport, streaks, people met, reliability) are computed by NestJS on demand, from registrations and occurrences. [BR-STA-01 to BR-STA-05, BR-ATT-04, BR-STA-09]
- **Global statistics** (heatmap, city ranking, popular sports and trends, back-office stats) are **read** from the analytics tables refreshed by the database. Never recompute them in NestJS. [BR-STA-06 to BR-STA-10]

## 12. Labels and language

- Reference tables hold a stable English `code` and an English `name`. The front end shows French text from its i18n files, keyed by `code`. Never branch on `name`; always branch on `code`. [BR-TECH-12]
