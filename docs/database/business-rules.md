# TeamDrop: database business rules

> **Audience:** NestJS developers and AI coding agents. Every rule has a stable ID (`BR-<DOMAIN>-<NN>`) that you can cite in code comments, commits and tests.
> **Status:** v1.1 (2026-11-02). Phase 1 deliverable, **approved**. Nothing here is migrated yet.
> **Companion file:** `docs/database/diagram/teamdrop-erd.drawio` (crow's foot, table-level).
> **Changelog:** v1.1 (2026-11-02): data layer introduced (enforcer DATA), developers no longer write SQL, badge awarding assigned to developers.

## How to read this document

Each rule has a **status**:

| Status | Meaning |
|---|---|
| `DECIDED` | Approved. Build on it. |
| `PROPOSED` | Design choice made while modelling, not yet explicitly approved. Can still change. |
| `OPEN` | Question still unanswered. The model shows a placeholder. See [Open questions](#11-open-questions). |
| `PENDING-TEAM` | Designed into the schema but waiting for a team-wide decision. Do not ship the feature yet. |
| `DEFERRED` | Out of scope for now. Not in the schema. |

Each rule also names **who enforces it**:

| Enforcer | Meaning |
|---|---|
| `DB` | PostgreSQL rejects invalid data: constraint, index, type or trigger. NestJS cannot bypass it. |
| `DB-JOB` | A scheduled PostgreSQL job (`pg_cron`) or SQL function owned by the database. |
| `DATA` | The data layer (`apps/api/src/data`): NestJS repositories, the only code that runs SQL. Developers call it. |
| `NEST` | Developers' NestJS code (controllers, guards, services). The database and data layer store the result but do not check the rule. |

## 1. Responsibility split: what PostgreSQL does that NestJS doesn't, and why

**Guiding decision (DECIDED):** business logic lives in NestJS: the data layer (consistency, visibility, statistics) and the developers' code (permissions, orchestration). PostgreSQL guarantees structural integrity and owns a few data-heavy jobs that would be slower, or less safe, outside it.

### 1.1 PostgreSQL does

| # | Responsibility | Why in the database and not in NestJS |
|---|---|---|
| D1 | **Primary keys** as UUID v7 generated by `uuidv7()` (PostgreSQL 18) | One ID strategy for every writer: NestJS, Paul's WebSocket service, the dataset generator, SQL scripts. UUID v7 is time-ordered (good B-tree locality, roughly sortable by creation) and safe to expose in URLs. |
| D2 | **Foreign keys** and their `ON DELETE` behaviour | Orphan rows are impossible even when someone forgets a check. The `ON DELETE` choice (`CASCADE` / `SET NULL` / `RESTRICT`) encodes what happens on erasure (section 9). |
| D3 | **Uniqueness**: usernames, email hash, one active registration per user and occurrence, one cheer per giver/recipient/occurrence, one owner per circle and per community, push endpoints, client message IDs | An application-level "check then insert" has a race: two concurrent requests both pass the check. Only a unique index is race-proof. |
| D4 | **Value checks** (`CHECK`, `NOT NULL`, enums): min ≤ max, duration > 0, no self-follow or self-block, exactly one target per report or conversation, a `circle_priority` event has a priority duration | Cheap, declarative, and protects against bugs in every client, including the seed generator and manual fixes. |
| D5 | **Exclusion constraint** on availability slots (no overlapping slots for the same user and day) | Overlap checks are race-prone in application code; `btree_gist` makes them atomic. |
| D6 | **Spatial types and indexes**: `geography(Point, 4326)`, GiST indexes, H3 cell computation | Distance search ("events within 10 km") must use an index. NestJS can't do that efficiently. |
| D7 | **Case- and accent-insensitive search support**: `citext`, `pg_trgm`, `unaccent` indexes | The indexes must live where the data is. |
| D8 | **Column encryption primitives** (`pgcrypto`) for email and birth date | Encryption and decryption happen in SQL. The key is supplied by the data layer per query and is never stored in the database. |
| D9 | **Heavy aggregates** (`DB-JOB`): heatmap cells, city activity for rankings, sport popularity and trends, back-office daily stats | They scan the whole history. Precomputing them next to the data (materialized views or summary tables refreshed by `pg_cron`) avoids moving millions of rows to NestJS. |
| D10 | **GDPR functions** (`DB-JOB`): full-account JSON export, erasure and anonymization procedure, retention purges | They must touch every table consistently, in a single transaction. A SQL function stays correct when a migration adds a table, because it lives next to the migrations. |
| D11 | **Technical timestamps**: `created_at` defaults, `updated_at` trigger | Purely mechanical; no business meaning. |

### 1.2 The data layer does

- consistency under concurrency: capacity, waitlist, one active registration, ownership hand-over, block side effects;
- filtering what a viewer may see: blocking, profile visibility, hidden location, circle-only and community-only events;
- eligibility that needs private data (adults-only);
- encryption and decryption of email and birth date;
- per-user statistics, reliability and badge progress data;
- every SQL query.

**Why:** Developers never write SQL; keeping consistency and visibility next to the queries makes them atomic and impossible to forget.

### 1.3 Developers do

**Who may *do* an action is the developers' job. What a viewer may *see*, and keeping the data consistent, is the data layer's job.**

- permissions and role checks (who may do an action);
- controllers and request validation;
- JWT, Passport and Google OAuth (with Paul for the WebSocket side);
- notifications, emails and push sending, using the outcomes returned by the data layer;
- scheduling periodic jobs (calling data-layer methods on a timer);
- badge awarding;
- the WebSocket gateway (with Paul);
- the front ends.

### 1.4 Rules the data layer must follow

- **Concurrency:** for any rule that counts rows (capacity, waitlist position, "last admin leaves"), lock the parent row first (`SELECT … FOR UPDATE` on `event_occurrence`, `circle`…) inside one transaction. Otherwise two requests can both take the last spot.
- **Hard delete everywhere (DECIDED).** There are no `deleted_at` columns. A deleted row is gone. Anything that must survive a deletion is handled by `ON DELETE SET NULL` or by the anonymous analytics tables.
- **Time:** store every instant as `timestamptz` (UTC). Compute days, weeks, streaks and "late" thresholds in `Europe/Paris` (rule BR-TECH-05).

## 2. Technical decisions

| ID | Rule | Status |
|---|---|---|
| BR-TECH-01 | PostgreSQL 18 + PostGIS 3.6. Extensions: `postgis`, `h3`, `h3_postgis`, `pgcrypto`, `citext`, `pg_trgm`, `unaccent`, `btree_gist`, `pg_cron`, and `pgtap` (test databases only). | DECIDED |
| BR-TECH-02 | **All primary keys are `uuid` generated with UUID v7** (`DEFAULT uuidv7()`). This includes reference tables. Junction tables use a composite primary key of their foreign keys. | DECIDED |
| BR-TECH-03 | Naming: `snake_case`, **singular** table names, no table prefixes. Constraints and indexes: `pk_<table>`, `fk_<table>_<column>`, `uq_<table>_<columns>`, `ck_<table>_<rule>`, `ix_<table>_<columns>`, `ex_<table>_<rule>` (exclusion). | DECIDED |
| BR-TECH-04 | The schema is owned by SQL migrations run with **dbmate**. **Kysely** (types generated by `kysely-codegen`) is used only inside the data layer (`apps/api/src/data/internal`). Developers never write SQL or query-builder code: they call the repositories exported by `apps/api/src/data/index.ts`. The ORM never creates or alters tables. | DECIDED |
| BR-TECH-05 | Instants are stored as `timestamptz` (UTC). Calendar logic runs in `Europe/Paris`. Recurring events store a **local** start time plus a `time_zone` (default `Europe/Paris`), so a 6 pm session stays at 6 pm across daylight-saving changes. | DECIDED |
| BR-TECH-06 | Hard delete everywhere. No soft-delete columns. | DECIDED |
| BR-TECH-07 | Database roles: `teamdrop_owner` (owns objects, runs migrations), `teamdrop_app` (NestJS: data read/write and function execution, no schema changes), `teamdrop_readonly` (analytics and debugging). No Row Level Security. | DECIDED |
| BR-TECH-08 | Messages carry a server ID (UUID v7, ordering and pagination) and a `client_message_id` generated by the client, unique per sender. A message re-sent after reconnection is deduplicated instead of duplicated. | DECIDED |
| BR-TECH-09 | No Redis. Real-time fan-out between processes, if needed, uses PostgreSQL `LISTEN/NOTIFY` (8 KB payload limit, not persisted). Clients reload missed messages from the `message` table. | DECIDED |
| BR-TECH-10 | Text search uses `pg_trgm` + `unaccent` (typo-tolerant, accent-insensitive) on event titles, usernames, venue names and community names. French full-text stemming may be added later. | DECIDED |
| BR-TECH-11 | Authentication: Passport (`local` + `google-oauth20`) and `@nestjs/jwt`, with tables owned by this schema. Passwords are hashed with argon2id in NestJS. Short-lived access JWTs (about 15 minutes) also authenticate the WSS handshake. Refresh tokens are stored hashed, rotated on use, and grouped by family to detect reuse. | DECIDED (to confirm with Paul for the WSS side) |
| BR-TECH-12 | User-facing labels (sports, levels, badges, cheer types, report reasons, notification types, consent purposes) live in **their own reference table**, each with a stable English `code` used by the code and an English `name`. **The database is in English; the front end is in French** and translates each `code` with its own i18n files. Consequence: a sport, badge or reason added from the back office shows its English `name` until a French translation is added to the front end. | DECIDED |
